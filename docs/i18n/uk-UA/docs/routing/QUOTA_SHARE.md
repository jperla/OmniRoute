## Огляд

Рушій спільного використання квоти справедливо розподіляє часову квоту провайдера (наприклад, 5-годинне вікно Codex або 1500 запитів/год для Kimi) між кількома API-ключами, які використовують одне й те саме підключення.

**Проблема, яку він вирішує:** OmniRoute проксіює багато API-ключів через той самий обліковий запис зовнішнього провайдера. Без логіки спільного використання сплеск запитів від ключа A може вичерпати квоту провайдера на годину, через що ключі B і C залишатимуться заблокованими до скидання вікна.
Рушій запобігає цьому таким чином:

1. Відстежує ковзне споживання кожного ключа за кожним виміром (%, запити, токени, $).
2. Застосовує справедливий алгоритм розподілу зі збереженням завантаження: ключ може позичати невикористані частки, доки глобальний пул не насичений.
3. Застосовує результат на критичному шляху (`chatCore.ts`) до того, як запит потрапить до зовнішнього виконавця.

## Алгоритм: справедливий розподіл роботи – збереження

Реалізовано в `src/lib/quota/fairShare.ts`.

### Режими

| Хвороба                                    | Режим       | Поведінка                                                              |
| ------------------------------------------ | ----------- | ---------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **Щедрий**  | Ключ можна позичати до загального ліміту за вирахуванням спожитої суми |
| `globalUsedPercent >= saturationThreshold` | **Суворий** | Суворо дотримуйтесь індивідуальної справедливої частки                 |

Типовий `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`).

Ці два режими описують пул у режимі запозичення за замовчуванням, `saturation`. Пул у режимі `consent` завжди застосовує суворі правила, незалежно від насиченості. Див. [Кредитування за згодою (згода на пул)](#consented-lending-per-pool-opt-in).

### Рішення за виміром

Для кожного активного виміру в пулі механізм обчислює:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

Для розмірів `percent` замість цього `consumed` походить із книги атрибуції (див. [Відсоткові розміри: атрибуція за ключем](#percent-dimensions-per-key-attribution) ).

Потім:

- **`policy = hard`** : якщо `consumed > fairShareAllowed` і режим суворий →** блокувати** .
- **`policy = soft`** : якщо `consumed > fairShareAllowed` і режим суворий →** штрафувати** (депріоритезація в комбо; ніколи жорстке блокування).
- **`policy = burst`** : дозволити, поки існує глобальний резерв незалежно від справедливої частки.

### Шапка абсолютна

`capValue` + `capUnit` для розподілу — це жорстка стеля незалежно від режиму чи політики. Будь-який вимір, де завжди `consumed >= capValue`** блоки** запит. Для кришки `percent` `consumed` є лише частиною, яка приписується ключу.

### Багатовимірна перевірка

Запит блокується, якщо** будь-який** розмір у пулі заблокує його. Розміри є незалежними — 5h% виснаження не впливає на тижневий% розмір.

### запозичення

У великому режимі ключ, чий розподіл не використовується, може використовувати надлишок із нерозподілених часток інших ключів. Формула така:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

де `consumedByOtherKeys = consumedTotal - consumedByThisKey`. Teto global (pool `limit` для цього виміру) завжди є жорсткою стелею.

### Кредитування за згодою (для кожного пулу)

Кожен пул має режим позики. `saturation` є типовим і зберігає правила, наведені вище. У режимі `consent` ключ `hard` передає свою частку лише в межах ємності, яку інші ключі погодилися надати. Адміністратор встановлює режим кожного пулу. Кожен власник ключа встановлює власну згоду через [згоду на позику](#lending-consent).

Згода – це відсоток від 0 до 100 і необов’язковий кінцевий термін у мілісекундах епохи. Ключ позичає цей відсоток своєї неактивної частки, поки кінцевий термін у майбутньому.

Для одного виміру `L` є ефективним лімітом: ліміт плану, помножений на облікові записи в пулі. Шлюз обчислює для запитуваного ключа:

```
share_k         = w_k / 100 × L
idle_k          = max(0, share_k − consumed_k)
lent            = Σ over the other keys of lend_k / 100 × idle_k
taken           = Σ over the other keys of max(0, consumed_k − share_k)
borrowAvailable = max(0, lent − taken)
```

`w_k` — вага ключа, або `100 / n` для кожного ключа, якщо вага не перевищує 0. `lend_k` — активний відсоток ключа, і 0, коли минув кінцевий термін. Власна згода запитувача ключа ніколи не зараховується. Ключ `hard` відхиляється, коли його споживання досягає своєї частки плюс `borrowAvailable`.

Ємність, яка не вимагає розподілу (100 мінус сума ваг), не підлягає позичанню. Ключ не погодився позичити.

**приклад.** `L` дорівнює 1000.

| ключ | вага | Поділіться | Споживається | Позичає |
| ---- | ---- | ---------- | ------------ | ------- |
| А    | 50   | 500        | 530          | 0%      |
| Б    | 30   | 300        | 100          | 50%     |
| C    | 0    | 0          | 60           | 0%      |

- B позичає 50% своїх неактивних 200, що дорівнює 100. C уже взяв 60 понад свою частку. А може позичити 40.
- А подається за 530 і відмовляється, коли його споживання досягає 540.
- До того, як C використав будь-що, з A на рівні або менше своєї частки, C міг позичити 100.
- До того, як C використав щось, з A на 530, C міг позичити 70.

**Нульова вага.** Ключ із вагою 0 має частку 0. Він обслуговується лише тоді, коли його споживання нижче того, що позичають інші. Коли ніхто не позичає, йому відмовляють з першого прохання.

**Терміни.** Жодне фонове завдання не закінчує термін дії згоди. Кожен запит порівнює кінцевий термін з власним часом, і кінцевий термін, що дорівнює цьому часу, минув. Збережений крайній термін, який не є скінченним числом або минув найбільшу дату, яку може вмістити `Date`, вважається пройденим.

**`soft` і `burst`.** Кредитування їх не обмежує. Пріоритет ключа `soft` втрачається після закінчення його частки. Ключ `burst` проходить, поки пул має місце. Стеля басейну все ще відхиляє кожен ключ, коли загальна сума пулу досягає свого ліміту.

**Вартість на шляху запиту.** Пул `saturation` не читає нічого більше, ніж раніше. У пулі `consent` лічильний вимір зчитує інші ключі лише для ключа `hard` на рівні або вище його частки, тоді як інший ключ надає. Потім виконується одне читання для кожного іншого ключа паралельно. Невдале читання вважається споживанням 0 для цього ключа. Розмір `percent` не додає читання, оскільки книга атрибуції містить усі ключі.

**Редагування пулу.** Редагування зберігає згоду ключів, які залишаються. Це стосується редагування розподілу, групових замін і викликів `ensure`. Видалений ключ втрачає згоду, а ключ, доданий назад, починається з 0. Маршрути адміністратора повертають згоду кожного ключа й ніколи його не записують. Перемикання пулу назад на `saturation` зберігає всі збережені згоди, які не впливають у цьому режимі. Повторне перемикання пулу на `consent` повторно активує збережені згоди, термін дії яких не минув. Власник ключа може очистити збережену згоду в будь-якому режимі.

**Оновлення.** Якщо стовпці `lending_percent` та `lending_until` вже існують, міграція додає лише `borrow_mode`, а збережені відсотки залишаються без змін. Кожен пул запускається в режимі `saturation`. Увімкніть `consent` для кожного пулу в майстрі пулу. Зі збережених значень нічого не випливає.

**Обмеження.**

- Позикодавець може знайти максимальну суму пулу до того, як використає власну частку. Ємність, позичена іншими, зараховується до загальної суми пулу.
- Перевірка виконується перед запитом і нічого не резервує. Одночасні запити зчитують споживання перед тим, як будь-який з них буде записаний, тому позичена ємність може бути використана кілька разів, обмежена запитами в польоті. Перевірка спільного використання режиму `saturation` має таку саму властивість.

## Лічильник ковзного вікна

Реалізовано в `src/lib/quota/sqliteQuotaStore.ts` і `redisQuotaStore.ts`.

Два сегменти для кожної пари `(apiKeyId, dimensionKey)`:

- `curr`: поточний сегмент (`floor(nowMs / windowMs)`)
- `prev`: попередній сегмент (`curr - 1`)

Ефективне ковзне значення:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**Точність**: приблизно 99%. Похибка становить щонайбільше 1% від розміру вікна на межі між сегментами (що притаманно наближенню з двома сегментами).

### Конкурентність

Драйвер SQLite: внутрішньопроцесне взаємне блокування для кожного ключа `(apiKeyId | dimensionKey)` запобігає стану гонитви під час читання-зміни-запису. Шаблон відповідає механізму захисту від лавиноподібних запитів у `src/sse/services/auth.ts`.

Драйвер Redis: Lua-скрипт EVAL для атомарного збільшення — виконується як одна команда Redis.

## Драйвери

### SQLite (за замовчуванням, не потребує встановлення)

- Таблиця: `quota_consumption` (див. міграції `073_quota_pools.sql` / `074_quota_consumption.sql`).
- Найкраще підходить для розгортань з одним екземпляром.
- Усі дані зберігаються в наявній базі даних SQLite OmniRoute (`DATA_DIR/storage.sqlite`).

### Redis (необов’язково, для кількох екземплярів)

- Потребує npm-пакет `ioredis`.
- Лічильники зберігаються в Redis; метадані (пули/розподіли) залишаються в SQLite.
- Найкраще підходить для розгортань із кількома репліками, де лічильники мають бути спільними.

### Перемикання драйверів

Через інтерфейс налаштувань (`/dashboard/settings` → Сховище квот) або через змінні середовища:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

Налаштування БД має вищий пріоритет, ніж змінна середовища. Якщо `driver=redis`, але URL відсутня або
`ioredis` не встановлено, фабрика повертається до SQLite і записує попередження в журнал.

Порядок вибору драйвера:

1. Налаштування БД `quotaStore.driver`
2. Змінна середовища `QUOTA_STORE_DRIVER`
3. За замовчуванням: `sqlite`

## Багатовимірність

Пул може мати кілька вимірів. Кожен вимір незалежний:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // global pool ceiling for this dimension
}
```

**Приклад: план Codex** (5 годин% + щотижня%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

Запит має відповідати всім розмірам, щоб бути дозволеним.

### Відсоткові розміри: атрибуція за ключем

Відсотковий план повідомляє одну цифру використання на обліковий запис і вікно плану. Провайдер не надає лічильника для кожного ключа API.

Щоб розділити цю цифру між ключами, кожен пул веде книгу атрибуції для кожного облікового запису та вікна плану. `src/lib/quota/percentLedger.ts` дотримується правил книги. `src/lib/quota/percentAttribution.ts` перетворює книгу на числа, які використовує контроль. Результатом є оцінка, побудована на основі маркерів кожного ключового маршруту.

#### Читання, що зворушують книгу

Книга рухається лише за власною фігурою провайдера для запитуваного вікна плану. Ці зв’язки повідомляють про одне:

| Провайдер                    | Планування вікон |
| ---------------------------- | ---------------- |
| Claude через з’єднання OAuth | `5h`, `weekly`   |
| Codex                        | `5h`, `weekly`   |

Це не вважається читанням:

- відповідь, яку клієнт постачальника позначає як застарілу
- вікно Claude, відсоток якого постачальник не повідомив
- фігура іншого вікна, або в гіршому випадку через вікна
- резервний заголовок обмеження швидкості
- невдале читання

Інші провайдери, включаючи Claude з ключем API, не мають книги. Кожен ключ нараховується 0 у відсотках, як і до цієї зміни.

Зчитування поділяє 30-секундний кеш сигналу насичення. Зчитування Claude датується датою, коли цифра була помічена в заголовках відповіді або зчитана з кінцевої точки використання, якщо цей час відомий. Інші показання датуються датою створення запису кешу.

#### Що зберігає книга

Кожен записаний запит додає свої маркери один раз до лічильника для кожного пулу, облікового запису та ключа. Фішка тільки росте. Книга зберігає три речі:

- базова лінія: цифра, коли книга відкривалася або вікно востаннє поверталося
- остання застосована цифра
- на ключ, його лічильник маркерів у той самий момент називається його міткою

Книга оновлюється, коли примусове виконання або маршрут використання обчислюють атрибуцію. Записи порівнюються та встановлюються за номером версії. Письменник, який програє, повторює один раз при новому читанні.

#### Як обчислюється частина ключа

Кожна частина ключа обчислюється під час читання книги. Зростання фігури, починаючи з базової лінії, розподіляється між ключами пропорційно до жетонів, які кожен з них направляє з моменту своєї позначки.

Together, ці маркери пояснюють щонайбільше одну точку фігури на маркери `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` (за замовчуванням 1000). Зростання, яке вони не пояснюють, є зовнішнім. Базова лінія також зовнішня.

Наприклад, книга відкривається на 0. Потім клавіша A направляє 900 000 токенів, а клавіша B – 100 000. При цифрі 60 частина А становить 54 бали, а частина В — 6.

Лічильник, який знаходиться нижче позначки ключа, перезавантажився та рахується повністю. Ключ без позначки, такий як ключ, який приєднується до пулу в середині вікна, підраховує всі свої жетони. Фігура, яка відстає від маркерів, викликає помилку, яка зникає під час наступного читання. Він не накопичується.

`QUOTA_PERCENT_MIN_TOKENS_PER_POINT` читається на кожному атрибуті. Значення, яке не є кінцевим числом принаймні 1, повертається до 1000.

#### Як читання змінює книгу

Застосовується перше правило відповідності:

1. **Книги ще немає:** читання відкриває книгу. Її фігура є базовою лінією, кожна фішка позначена.
2. **Давніше читання:** показання, датовані раніше останнього застосованого, ігнорується. Так само і зчитування, час скидання якого більш ніж на 30 хвилин раніше, ніж збережене.
3. **Вікно нового постачальника:** час скидання більш ніж на 30 хвилин пізніше, ніж збережений, повертає книгу. Фігура стає базовою лінією, і кожна фішка знову позначається. Ключі без лічильника залишають книгу.
4. **Завершене вікно:** збережений час скидання, який не є після часу зчитування даних, означає, що вікно закінчилося. Читання перевертає книгу, якою б вона не була.
5. **Вища цифра:** рухається тільки остання фігура. Базова лінія та позначки залишаються.
6. **Та сама фігура:** фігура, базова лінія та позначки залишаються. Написано лише час скидання, якого бракує книзі.
7. **Нижня цифра:** нижча цифра ніколи не застосовується як така. Вона повертає книгу лише тоді, коли три речі тривають. Він принаймні на дві хвилини новіший за останній застосований показник. Ніщо не говорить, що вікно те саме відкрите. Це більш ніж на один пункт нижче.

Вікно вважається таким же відкритим, коли тримають три речі. Обидва часи скидання відомі. Вони знаходяться в межах 30 хвилин один від одного. Збережений ще випереджає зчитування. Нижня цифра в цьому вікні нічого не змінює.

Час скидання зберігається лише тоді, коли він випереджає час даних зчитування, яке його містить. Більший показник зберігає час скидання показань, коли цей показник придатний для використання, і зберігає збережений час в іншому випадку. Рівна цифра записує час скидання читання лише тоді, коли книга його не має. Більше це нічого не змінює. Менша цифра, яка не повертає книгу, записує час скидання.

#### Коли книга використовується

Після читання книга використовується, якщо її збережений час скидання не після поточного часу. Цей випадок виникає, коли зчитування, зроблене безпосередньо перед скиданням, наприклад, подане з кешу, спостерігається одразу після нього.

Без читання, яке можна використовувати, збережена книга використовується лише тоді, коли вона все ще може бути книгою поточного вікна. Це справедливо в двох випадках:

- його час скидання відомий і ще попереду
- він не має часу скидання, а останнє показання, яке змінило його, минуло щонайбільше 15 хвилин

Інакше нічого не приписується, як коли книжки немає. Книга, збережений час скидання якої минув, ніколи не стягується.

#### Примусове виконання

Споживання ключа у відсотковому вимірі — це його приписана частина плюс частка зовнішньої частини. Зовнішня частина спочатку використовує ємність без вимог розподілу (100 мінус сума ваг). Тільки надлишок розподіляється між ключами за вагою.

Це споживання порівнюється зі справедливою часткою ключа, як і для будь-якого іншого виміру. Строгий режим все одно запускається, коли сигнал насичення досягає `QUOTA_SATURATION_THRESHOLD` (за замовчуванням 0,5). Кожне число масштабується за ефективним лімітом: ліміт на обліковий запис, помножений на кількість облікових записів у пулі.

Абсолютне обмеження з `capUnit: "percent"` враховує лише частину, приписану ключу, масштабований таким же чином. Візьміть обмеження на обліковий запис у 100 і k облікових записів. Ліміт у N досягається, коли ключова частина фігури обслуговуючого облікового запису досягає N/k балів. Кожен рахунок звіряється з окремою книгою. Наприклад, з двома обліковими записами обмеження в 10 досягається при 5 пунктах фігури одного облікового запису.

Якщо сховище неможливо прочитати, нічого не приписується, і кожен ключ нараховується 0 у цьому вимірі. Якщо записати книгу не вдається, це атрибуція використовує книгу такою, якою вона була прочитана. Невдалий запис маркера залишає маркери цього запиту поза книгою. Жодна з цих помилок не блокує запит.

У пулі `consent` формула кредитування використовує споживання кожного ключа у відсотковому вимірі, як описано вище. Коли надається інший ключ, книга читається один раз і приписується кожному ключу. Без придатної для використання книги кожен ключ стягується 0. Ключ з вагою потім проходить, а ключ з вагою 0 проходить лише тоді, коли інший ключ позичається.

#### Маршрут використання

`GET /api/quota/pools/{id}/usage` повідомляє ті самі числа через ту саму функцію. Вимір відсотка має один запис для кожного підключення пулу в `accounts`. Його `consumedTotal` і `perKey` верхнього рівня відображають перший запис.

Маршрут також застосовує поточне читання, тому він може просувати книгу вперед, як це робить запит. `internal + external` може відрізнятися від `consumedTotal`, якщо немає придатних для використання показників або коли не застосовується нижчий показник.

#### Зберігання та утримання

Обидва магазини квот зберігають книгу. На SQLite автоматичне очищення бази даних, якщо ввімкнено, видаляє рядки, які не оновлювалися протягом 60 днів. На Redis книги та лічильники підключення до пулу мають спільний ключ. Він діє через 60 днів після останнього запису або зміни книги. Книга, яка не змінюється, не переписується, тому відсікання встановлюється над найдовшим вікном плану. Ручне скидання історії використання також очищає книги на SQLite (див. Обмеження).

#### Обмеження

- Весь приріст показника облікового запису з моменту базового рівня ділиться на токени, маршрутизовані з того часу за кожним ключем. Коли це зростання відбулося, значення не має.
- Таким чином, використання, здійснене за межами OmniRoute стягується з ключів у межах, дозволених їх маркерами. Це включає використання до першого запиту ключа вікна, коли книга вже була відкрита.
- Наприклад, зовнішнє використання підвищує рахунок на 60 балів, а ключові маршрути відсутні. Потім ключ направляє 30 000 токенів, і цифра досягає 60,6.
- Якщо книга була відкрита до цього використання, частина ключа становить 30 балів. Він також має 7,65 зовнішнього використання з чотирма ключами вагою 25.
- Якщо книга відкрилася після цього використання, 60 балів є базовими. Частина ключа становить 0,6 бала, а зовнішнього використання вона несе 15.
- Запит або відвідування маршруту використання відкриває книгу. Отже, чи вважається таке використання базовим, залежить від того, коли книга була відкрита.
- З мінімальним значенням за замовчуванням ключ, який направляє 60 000 токенів під час зовнішнього використання, підвищує обліковий запис на 60 балів, отримує всі 60 як свою частину.
- При поверсі 50 000 його власна частка становить 1,2 бали. Інші 58,8 є зовнішніми та заряджаються за вагою, як і будь-яке зовнішнє використання.
- Встановіть `QUOTA_PERCENT_MIN_TOKENS_PER_POINT` приблизно до вартості одного бала у вашому плані. Зовнішнє використання включає трафік на той самий обліковий запис від ключів поза пулом.
- Відсоткове обмеження застосовується в кожному режимі. У закритому ключі може бути відмовлено, якщо обліковий запис значно нижче порогу насичення.
- Візьміть шапку 10 і 12 очок зовнішнього використання раніше у вікні. Потім ключ, який направляє 20 000 токенів, відхиляється за показником облікового запису 12,4%.
- Розподіл є оцінкою обсягу токена. Запит зараховується як маркери підказки плюс маркери завершення. Кеш-знижки та ціни на моделі не змінюють цей показник.
- Запит, який не закінчується статусом 200, не записує маркерів. Прикладами є потік, який клієнт від’єднує, і помилка висхідного потоку після використання.
- Використання, викликане таким запитом, стягується з тих ключів, які записували токени, у межах, дозволених їхніми токенами. Решта зовнішнє. Назад не рухається. Відповідь, яка повідомляє про відсутність використання маркерів, також не записує жодних маркерів.
- Використання поточного запиту може відображатися в іншій активній частині ключа для всього запиту. Він повертається лише тоді, коли запит закінчується статусом 200.
- Використання вже в обліковому записі під час відкриття книги вважається зовнішнім. Це охоплює оновлення, новий пул і новий обліковий запис. Використання в новому вікні до його першого читання також вважається зовнішнім.
- Кожен ключ починається зі своєї вагової частки цього використання після ємності без претензій щодо розподілу. З одним обліковим записом на 85% і п’ятьма ключами вагою 20, кожен починає з 17 із своїх 20 використаних.
- У пулі з кількома обліковими записами цифра обслуговуючого облікового запису застосовується до підсумкового бюджету. Книга не змінила цього.
- Нижня цифра всередині вікна, яке провайдер повідомляє як відкрите, не застосовується. Час скидання, який повертається більш ніж на 30 хвилин, розглядається як старе показання.
- В обох випадках книга зберігає свій стан, доки не мине збережений час скидання. Після цього книга не стягується, доки її не переверне читання.
- Засіб — ручне скидання історії використання (`POST /api/settings/purge-usage-history`). Він очищає книги атрибуції та їхні лічильники токенів у базі даних SQLite.
- Період `all` очищає кожну книгу та лічильник. Коротший період спочатку очищає книги, не написані протягом нього. Потім він очищає лічильники, не записані в ньому, а лише для з’єднання з пулом, у якому не залишилося книги. Збережена книга все ще позначає кожен ключ проти свого лічильника.
- Книга, фігура якої не переміщувалася, не переписується, тому менший період також може очистити книгу поточного вікна. Наступне читання відкриває нову книгу на поточній цифрі.
- Скидання не стосується сховища квот Redis. Там книга закінчується своїм вікном або закінчується через 60 днів після останнього написання.
- Коли постачальник не надсилає час скидання, вікно, яке скидає та заповнює стару цифру між двома показаннями, виглядає як більш висока цифра. У книзі збережено стару основу та позначки.
- Показання датуються місцевим годинником. Коли він випереджає постачальника або джерело повідомляє час скидання трохи раніше, книга може розгорнутися до цієї різниці раніше.
- Зростання в цьому короткому проміжку поділяється на токени, спрямовані в ньому. Перше читання наступного вікна виправляє це. Якщо перегорнута книга не містить часу скидання, для цієї корекції потрібне нижче число, щонайменше на дві хвилини нове, ніж останнє застосоване читання.
- Екземпляри, які спільно використовують Redis зберігають показання дати зі своїми власними годинниками, тому синхронізуйте ці годинники. Показання екземпляра, годинник якого відстає, виглядають старішими та ігноруються.
- Якщо після збереженого часу скидання не надходить придатне для використання зчитування, відсоткові частки та обмеження відсотка на ключ не застосовуються, доки зчитування не повернеться. Без скидання часу це починається через 15 хвилин після останнього читання, яке змінило книгу.
- У магазині Redis книга, яка не використовувалася протягом 60 днів, може закінчитися між перевіркою автора та її записом. Потім його повторно створюють у версії вище 1, що є дійсним станом.

### гачок PRE (`open-sse/handlers/chatCore.ts`)

Запускається перед вищим виконавцем, після перевірки авторизації та політики:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() per dimension
      → fairShare.decideFairShare()
      → if block → return 429 (buildErrorBody, Hard Rule #12)
      → if allow + deprioritize → set quotaSoftPenalty=true on candidate
  → executor.execute()
```

**Відмовно відкритий** : якщо `enforceQuotaShare` видає, запит дозволяється через журнал `pino.warn`. Це запобігає блокуванню всього трафіку через помилку механізму квотування.

**Коли відновиться ємність.** Відмова в частці ключа або на стелі басейну закінчується одним із двох речень в обох режимах запозичення:

- Вікно `percent` : `. The <window> window resets at <time>.` Час – це скидання звітів постачальника.
- Лічильна одиниця: `. Enough <window> usage is expected to clear by <time>.` Час є верхньою межею ковзного вікна, якщо ключ більше нічого не надсилає.

`<time>` — це миттєвий файл ISO 8601 у UTC. Тоді відмова містить `Retry-After`: цілі секунди до цього моменту плюс один. Клієнт, який чекає так довго, повторює спробу щонайбільше через одну секунду після моменту. Коли момент невідомий, відмова не містить ні речення, ні заголовка. Абсолютна відмова від обмеження не несе ні того, ні іншого. Загальнодоступний код залишається `quota_share_blocked`.

Відмова в спільному доступі не впливає на спільне з'єднання. Він не встановлює час відновлення, не блокує модель і не вимикає провайдера, а інші ключі пулу продовжують обслуговуватися. Коли кожна мета комбо відмовляється від ключа для своєї частки, комбо відповідає 429 без очікування. Його відповідь містить підказку як `Retry-After`. Шлях вбудовування завершує свою відмову тим самим реченням і не надсилає `Retry-After`.

### POST хук (рекордне споживання)

Після успішної відповіді:

```
executor returns success
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() per dimension
      → fail-open: errors logged as pino.warn, never propagated to client
```

**Дрифтова записка** : якщо `consume` не відповідає після відповіді, поточний лічильник занижується. Сигнал насичення від постачальника (наприклад, `anthropic-ratelimit-unified-5h-utilization`) коригує глобальну оцінку на наступний запит.

### Комбінований м'який штраф (`open-sse/services/combo.ts`)

Коли `decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // default 0.7
}
```

Покарання застосовується після всіх інших факторів нарахування очок. Це знижує ймовірність автоматичного комбінування вибору насиченого ключа без його жорсткого блокування.

## Квота самообслуговування API (за бажанням)

`GET /api/v1/me/quota/{provider}` (також обслуговується в `/v1/me/quota/{provider}`) дозволяє власнику ключа API читати за допомогою свого власного ключа, яка частина спільної підписки належить їм і що їх блокує. Маршрут є тонкою оболонкою над `src/server/selfService/quotaHandler.ts`; представлення створюється за допомогою `src/lib/quota/selfView.ts`, а його відповідний контракт — `src/shared/schemas/selfQuota.ts` (`SelfQuotaView` у `docs/openapi.yaml`).

### Включення та автентифікація

- Прапор функції `QUOTA_SELF_PANEL`, за замовчуванням `false`. Поки його вимкнено, запит, який досягає маршруту, отримує 404. З `REQUIRE_API_KEY=true` політика API клієнта відхиляє відсутній або недійсний ключ із 401 перед виконанням маршруту, незалежно від прапора. Запит без ключа, але сеанс інформаційної панелі, під час якого ви ввійшли, передає цю політику та отримує власну відповідь маршруту. Цей прапор вирішується, як і будь-який інший прапор (перевизначення приладної панелі або REST, потім однойменна змінна середовища); див. [`FEATURE_FLAGS.md`](../reference/FEATURE_FLAGS.md).
- Кожне відображуване ім’я пулу та кожна мітка розкладу повертаються власникам ключів пулу точно так, як їх написав адміністратор. Перш ніж увімкнути прапорець, переконайтеся, що вони придатні для читання цими власниками ключів.
- Ключ читається лише із заголовків: `Authorization: Bearer <key>` або `x-api-key: <key>`. Коли надсилаються обидва, використовується перший, який перевіряє. Ключ у рядку запиту або файл cookie ігнорується. Ключ середовища сервера відхилено (401).
- Для ключа потрібна область `self:usage` (403 без неї).
- Сегмент провайдера обрізається, пишеться в нижньому регістрі та перевіряється на `^[a-z0-9][a-z0-9._-]{0,63}$` (в іншому випадку 400), а потім вирішується через реєстр провайдерів, тому псевдонім, такий як `cc` читає пули `claude`. `claude` і `anthropic` читають ті самі пули.

### Що показує кожна видимість

| Видимість                | Вимагає                                                                            | поля                                                                                                                                                                                                                                                 |
| ------------------------ | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Власна частка            | `self:usage`                                                                       | `pools[]` (посилання, ім’я, постачальник, політика, вага, обмеження), `dimensions[].yourShare`, `accounts[]` із `yourShare` (у вікні `percent` без `attributed` і `external`), `blocks`, `availableModels`, `expiresAt`, `apiBaseUrl`                |
| Рівень облікового запису | `self:usage` + `self:account-quota` і постачальника в `sharedQuotaProviders` ключа | додає `dimensions[].total`, `accounts[].dimensions[].account` і `accounts[].modelWindows`, `attributed` і `external` в `yourShare` вікна `percent` і `members` у пулі з увімкненим використанням членів (див. [Використання членів](#member-usage) ) |

- `sharedQuotaProviders` це налаштування для кожного ключа (`PUT /api/keys/[id]/self-service`): `null`, за замовчуванням, означає кожного постачальника, якого досягає ключ; `[]` означає жодного. `accountVisible` кожного пулу вказує, яка видимість застосована до нього.
- Панелі облікових записів і вікна моделей відображаються лише для облікових записів, підключення до яких може використовувати ключ. Коли ключ має список дозволених з’єднань, обліковий запис поза ним зберігає свій запис `Account N` без `account` або `modelWindows`. Порожній список означає відсутність обмежень, як і для `/v1/me/status`. Загальний пул (`dimensions[].total`) не залежить від цього списку.
- Дві цифри, показані лише з `self:usage` походять від використання інших ключів. `exhausted` бюджету розкладу відображає споживання кожного ключа за цим розкладом. У пулі, всі ваги якого дорівнюють нулю, `weight` ключа дорівнює `100 / number of members`. Обидва вони застосовуються до ключа.
- Пул ідентифікується лише за допомогою `ref`, непрозорого значення, прив’язаного до ключа виклику. Його відображувана назва (`name`) включена так, як її написав адміністратор. `ref` походить від ключа та пулу з секретним ключем API сервера (`API_KEY_SECRET`). Клієнти не повинні зберігати його: він змінюється, якщо цей секрет ротується.
- Облікові записи вказано як `Account 1`, `Account 2`, … у порядку пулу. Ідентифікатор пулу, ідентифікатор з’єднання, адреса електронної пошти або ім’я облікового запису не повертаються, а відповідь проходить через схему контракту, яка видаляє будь-які поля поза ним.
- Обчислювані одиниці (`requests`, `tokens`, `usd`) повідомляються як відро пулу, яке забезпечує обмеження квот: `limit` = обмеження плану × облікових записів у пулі, `fairShare` = вага / 100 × `limit` (рівний розподіл, коли кожна вага дорівнює 0), `consumed` = власний лічильник ключа в сховищі квот, `remaining` = `fairShare` − `consumed`, на рівні 0.
- `blocks.schedules` містить список вікон розкладу ключа (`open`/`closed`, `blackout` або `outside-window`, `retryAfterSeconds`, резервні поверхи та чи витрачено бюджет вікна); `blocks.modelCaps` перераховує свої погодинні обмеження для кожної моделі зі споживанням.
- Ключ за межами кожного пулу постачальника отримує 200 з `pools: []`; `availableModels` (ідентифікатори `qtSd/`, які ключ бачить у `/v1/models`), `expiresAt` та `apiBaseUrl` все ще заповнені.
- `apiBaseUrl` є `OMNIROUTE_PUBLIC_API_BASE_URL`, тоді `OMNIROUTE_PUBLIC_BASE_URL`, інакше `null`. Це ніколи не є джерелом самого запиту.

### Згода на кредитування

`PATCH /api/v1/me/quota/{provider}` записує власну згоду ключа виклику для одного пулу. Він використовує прапор, заголовки та правила провайдера `GET`. Область `self:usage` дозволяє цей запис, хоча його назва читається як лише для читання.

```json
{
  "pool": "qpr_0123456789abcdef0123456789abcdef",
  "lendingPercent": 30,
  "lendingUntil": 1893456000000
}
```

- `pool` — це `ref`, який повертає `GET` для цього пулу.
- `lendingPercent` є цілим числом від 0 до 100. Значення 0 очищає згоду та її кінцевий термін. Тіло з `lendingPercent` 0 приймається в будь-якому режимі.
- `lendingUntil` є необов’язковим: епоха мілісекунди або `null` без крайнього терміну. Воно має бути в майбутньому та не більше 8640000000000000. Значення, нижче за 100000000000, читається як секунди й відхиляється.
- Будь-яке інше поле відхилено. Тіло, довше 4096 байт, відхиляється. Зчитування зупиняється на цьому розмірі, тому довше тіло ніколи не утримується цілим.

Перевірки виконуються в порядку цієї таблиці. Кожна відмова використовує стандартне тіло помилки з фіксованим повідомленням. Відмова однією з цих перевірок нічого не пише.

| Статус | повідомлення                                                                                       | Коли                                                              |
| ------ | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 404    | `Not found`                                                                                        | Прапор `QUOTA_SELF_PANEL` вимкнено.                               |
| 401    | `Valid API key required`                                                                           | Ключ відсутній або недійсний, або це ключ середовища сервера.     |
| 403    | `API key lacks the self:usage scope`                                                               | У ключі немає `self:usage`.                                       |
| 400    | `Invalid provider`                                                                                 | Сегмент постачальника недійсний.                                  |
| 429    | `Too many lending changes. Retry later.`                                                           | Ключ перевищив свій ліміт. Відповідь містить `Retry-After`.       |
| 400    | `Body must be { pool, lendingPercent, lendingUntil }. lendingPercent is an integer from 0 to 100.` | Тіло не є JSON, занадто довге або не відповідає схемі.            |
| 400    | `lendingUntil must be a Unix time in milliseconds`                                                 | Дедлайн читається як секунди.                                     |
| 400    | `lendingUntil must be in the future`                                                               | Кінцевий термін припадає на час запиту або раніше.                |
| 404    | `Pool not found`                                                                                   | `ref` не називає пул цього ключа для цього постачальника.         |
| 403    | `Lending is not enabled for this pool`                                                             | Пул знаходиться в режимі `saturation`, а `lendingPercent` вище 0. |
| 500    | `Failed to build quota view`                                                                       | Будь-яка інша невдача. Його причина зареєстрована на сервері.     |

Обмеження становить 20 запитів на 60 секунд для кожного ключа. Кожен запит, який пройшов перевірку постачальника, зараховується, навіть той, у якому відхилено пізніше, або той, який нічого не змінив. Він має свій власний лічильник, окрім обмеження частоти запитів ключа.

Запит, який змінює збережену згоду, записує один запис аудиту `quota.pool.lending.updated`. Він називає ключ зі старим і новим значеннями. Один і той же орган, надісланий двічі, один раз пише і один раз перевіряє. Відповідь: 200 із повним виглядом `GET`, створеним після запису.

Перегляд `GET` повідомляє про кредитування таким чином:

- Кожен пул містить `borrowMode` (`saturation` або `consent`), а також власні `lendingPercent` і `lendingUntil` ключа.
- `lendingActive` це `true` лише в пулі `consent`, із відсотком вище 0 і кінцевим терміном не досягнуто.
- У пулі `consent` кожен злічуваний `dimensions[].yourShare` несе `borrowAvailable`. Це те, що ключ може використовувати понад свою частку зараз, позичену іншими ключами.
- `borrowAvailable` використовує формулу воріт. Він читає кожен другий ключ, навіть коли ключ знаходиться під його спільним доступом. Для ключа `hard` це одне додаткове зчитування на інший ключ і лічильний розмір паралельно.
- `borrowAvailable` це `null` для ключа `soft` або `burst`, і `null` коли читання не вдається.
- `borrowAvailable` є однією цифрою для всіх інших ключів разом. У наборі з двох ключів це фігура іншого ключа.
- `borrowAvailable` ще не повідомляється для `percent` windows або в `accounts[]`.
- У пулі `saturation` перегляд повідомляє про збережену згоду з `lendingActive: false` і без `borrowAvailable`.

### Помилки

Кожна відповідь цього маршруту, успіх чи помилка, несе `Cache-Control: no-store`. Відмова, яка відбувається перед запуском маршруту, не несе його, наприклад, політика клієнта API 401 або фільтр 403 IP. Помилки маршруту використовують стандартне тіло помилки з фіксованим повідомленням: 400 (недійсний постачальник), 401 (відсутній або недійсний ключ), 403 (відсутній `self:usage`), 404 (вимкнено) і 500 (`Failed to build quota view`). 500 покриває будь-який збій, коли запит досягає маршруту, включаючи сам пошук ключа; його причина реєструється на сервері та ніколи не повертається. Помилки `PATCH` перераховані в [Згоді на кредитування](#lending-consent).

### Обмеження

- `remaining` — це частина справедливої частки ключа, яку він не використав. Це не гарантія. Ключ все ще може бути поданий за ним, поки в басейні є місце. Коли загальна сума пулу досягає `limit`, кожен ключ пулу відхиляється, незалежно від його власного `remaining`, і ключ без `self:account-quota` не може побачити цю загальну суму.
- `remaining` не враховує абсолютний `cap` розподілу. Виконання відмовляється від ключа, коли його власне споживання у вікні блоку обмеження досягає значення обмеження.
- Панель на рівні облікового запису надходить із кешу обмежень постачальника та може затримувати рішення про застосування на кілька хвилин. Зчитування, час скидання якого минув, повідомляється як `stale`.
- Вікна для кожної моделі (`modelWindows`) повідомляються лише для постачальників, які мають зіставлення вікна плану: Claude і Codex сьогодні. Для інших постачальників `modelWindows` все ще присутній, коли відображаються дані облікового запису з порожнім списком `windows`.
- Власна частка ключа у вікні `percent` є приблизною. Він узятий із книги атрибуції та містить усі обмеження, перелічені у розділі «Відсоткові розміри: атрибуція за ключем» вище.
- `consumed` — це кількість порівняння примусового виконання із справедливою часткою. Це точно `attributed` плюс `external`. `attributed` — це частина, яку книга дає ключ для токенів, які вона направляє. `external` — це частина використання ключа обліковим записом, яку ключі пулу не враховують.
- Обидві частини надсилаються лише тоді, коли `accountVisible` пулу є істинним: ключ має `self:account-quota`, а постачальник знаходиться у своєму `sharedQuotaProviders`. Ключ без нього отримує лише `consumed` з тими самими `status` та `reason`.
- Маючи обидві частини та власну вагу, власник може розрахувати використання поза басейном, яке стягується з ключів від басейну. Власник із обсягом облікового запису вже бачить загальну суму облікового запису.
- Ключ, який нічого не маршрутизував у вікні, все ще може зчитувати свій зовнішній заряд із `consumed`, тому що його атрибутована частина дорівнює 0.
- Наприклад, книга відкривається в 0, а ключі A і B мають вагу 50 кожен. Ключ A направляє 900 000 токенів, а ключ B – 100 000. Потім рахунок досягає 60% від ліміту 100. Тоді `attributed` дорівнює 54 для ключа A і 6 для ключа B, а `external` дорівнює 0 для обох.
- Представлення читає книгу і ніколи не записує свій стан. Він не відкриває книгу і ніколи не запитує провайдера про читання. У сховищі Redis читання видаляє замінені поля ревізій у фоновому режимі, як і читання шлюзу.
- Спільний доступ є `ok` лише тоді, коли кеш шлюзу зберігає зчитування облікового запису. Без нього це `stale`, тому в пулі без останніх запитів він відображається як, можливо, застарілий.
- Поки запит не пройде через пул, спільний доступ недоступний. Цей запит відкриває книгу, і цифра облікового запису в цей момент зараховується як використання поза пулом.
- У пулі з кількома обліковими записами кожен запис облікового запису використовує власну книгу цього облікового запису та ліміт одного облікового запису. Примусове виконання масштабує обидві сторони за кількістю облікових записів, тому пропорція однакова.
- Вікна для кожної моделі не мають частки ключа. Книга не зберігає дані для кожної моделі.
- Резервні поверхи розкладу не оцінюються представленням: розклад може відображатися як `open` тоді як запит відхилено з причини `schedule-reserve`.
- Коли два пули одного ключа спільно використовують з’єднання, примусове застосування застосовує один із них, і в поданні відображаються обидва.
- Немає обмежень на невдалу спробу введення ключа для кожної адреси: абоненти, що дзвонять за зворотним проксі-сервером, можуть надавати спільний доступ до однієї адреси (це залежить від того, чи надійні адреси перенаправлених клієнтів), тому блокування може заборонити маршрут кожному власнику ключа. За допомогою `REQUIRE_API_KEY=true` політика API клієнта відхиляє недійсний ключ перед запуском маршруту з тілом 401 цієї політики замість цього маршруту.

### Використання учасників

Адміністратор може дозволити власникам ключів бачити, як розподіляється використання вікна між учасниками пулу. Опцією є `memberBreakdown` пулу, вимкнено за замовчуванням. Його встановлюють у майстрі пулу або за допомогою `PATCH /api/quota/pools/{id}`. `GET /api/quota/pools` і `GET /api/quota/pools/{id}` повідомляють про це.

Вимір подання містить `members` лише тоді, коли виконуються всі ці параметри:

- опція басейну включена
- пул має не більше 20 виділених ключів, і принаймні три з них можуть надсилати запити: активні, невідкликані, не заборонені та не прострочені
- `accountVisible` пулу вірний: ключ має `self:account-quota`, а провайдер знаходиться в його `sharedQuotaProviders`
- у вікні `percent` ключ може використовувати з’єднання облікового запису
- власну частку ключа цього вікна було прочитано: його `status` не є `unavailable`

В іншому випадку `members` відсутній. Це ніколи не порожній список.

- Кожен фрагмент є `{ slot, consumed, isYou }`. Схема відповіді відхиляє будь-яку іншу властивість зрізу та список із понад 20 зрізів. Фрагменти перераховані в порядку слотів.
- Для кожного виділеного ключа є один фрагмент, включаючи ключ, який більше не може робити запити. Член без використання показує реальний нуль.
- Слот 1 завжди є запитуваним ключем із значенням `isYou`. Інші номери слотів є рангами гешу з ключем. Він має ключ `API_KEY_SECRET` і охоплює пул, ключ запиту та учасника.
- Таким чином, номери не збігаються між власниками. Для одного власника вони залишаються незмінними між візитами. Вони можуть змінюватися, коли ключ приєднується до пулу або залишає його, або коли цей секрет обертається.
- У лічильному вікні зріз — це лічильник члена в сховищі квот, такий самий лічильник, як і його власний `consumed`.
- У вікні `percent` зріз — це частина `attributed` члена з тієї ж книги, що читається як власний ресурс ключа. Використання поза басейном ніколи не розбивається на частини. Цей заряд ділиться на вагу, тому шматочки, які його несли, показували б вагу.
- Кожне представлення паралельно зчитує одне значення для кожного іншого члена та лічильного вікна. У вікні `percent` фрагменти не коштують жодного читання, окрім читання власної книги. Якщо одне значення неможливо прочитати, це вікно не має `members`, а власна частка ключа залишається.
- Опція та кількість доступних ключів зчитуються один раз для кожного пулу та лише для ключа, який може бачити дані облікового запису. Невдале читання опції або підрахунку корисних ключів вимикає смуги для цього пулу. Сервер реєструє попередження, а решта подання будується.

Смуги не мають імен чи ідентифікаторів. Вони все ще розповідають власнику ключа речі про інших учасників:

- Власники все ще можуть зіставляти фрагменти за їхніми значеннями.
- Стабільна нумерація дозволяє власнику стежити за одним членом з часом.
- Кількість фрагментів показує, скільки ключів виділено в пулі.
- У групі з трьох ключів той, хто знає, який ключ використовувався, може сказати, який ключ використовувався останнім.
- Коли пул падає нижче трьох придатних для використання ключів, смуги зникають. Перегляди, зроблені раніше, все ще показують, що використовував кожен учасник.
- У лічильному вікні загальний пул за вирахуванням фрагментів може показати використання ключів, які більше не виділені.
- Учасник, який показує нуль в одному обліковому записі та використовує в іншому, може показати, який учасник використовує який обліковий запис.
- У рахунковому пулі з політикою `hard` зріз, який перестає рости на справедливій частці учасника, вказує на вагу цього учасника.

### Серія використання (`GET /api/v1/me/usage`)

`GET /api/v1/me/usage?range=<range>` (також обслуговується в `/v1/me/usage`) повертає дані про використання та вартість власних запитів ключа виклику: підсумки, один запис на день UTC, на день і модель, на модель і на постачальника. Він ділиться прапором, правилами автентифікації, областю `self:usage`, `Cache-Control: no-store` та поведінкою помилок маршруту квоти вище. Ключ перевіряється перед `range`. Помилки: 400 (`Invalid range`), 401, 403, 404 і 500 (`Failed to build usage`).

- `range` є одним із `1d`, `7d`, `30d` (за замовчуванням) або `90d`. Будь-яке інше значення, порожнє значення або параметр, що повторюється, є 400. Набір зупиняється на `90d` щоб обмежити вартість дзвінка. Перегляд читає лише необроблену історію використання, а не щоденні підсумки, які не містять ключа.
- Рядки вибираються за ідентифікатором клавіші виклику. Стовпець імені ключа ніколи не збігається, а рядки, записані без ідентифікатора ключа, ніколи не враховуються.
- Побудова серії виконує п’ять згрупованих запитів над рядками ключа у вікні. Збудована серія повторно використовується протягом 60 секунд для кожного ключа та діапазону, а повторно використаний виклик не виконується. Його `generatedAt` вказує на його вік.
- Вікно закінчується, коли серія побудована. Рядок, відштампований пізніше, наприклад, через перекіс годинника, не враховується.
- `coverage.retentionDays` — це налаштування збереження необробленої історії використання оператором (`retention.usageHistory` у налаштуваннях бази даних). `coverage.truncatedByRetention` має значення true, коли запитуваний діапазон довший за це налаштування. Він порівнює два числа і не перевіряє, чи дійсно відсутні рядки.
- Постачальник повертається як записаний для власних запитів ключа. Модель — це записана назва після її останнього `/`, і рядки групуються за нею. Комбінований запит, кожну ціль якого було відхилено, записується з міткою маршрутизації як постачальника (комбінована назва, `auto` або `combo`) і рядком моделі, надісланим клієнтом. Інші відхилені запити, наприклад через відкритий вимикач, перезарядку моделі або пропуск запаркованої квоти, зберігають цільового постачальника та модель.
- Окрім підрахунків і вартості, відповідь містить середню затримку, рівень успіху та час першого й останнього запиту.
- `byModel` перераховує 50 пар постачальника та моделі з найбільшою кількістю запитів. З більшою кількістю пар його записи не додають до `summary`, а `summary.uniqueModels` підраховує кожне записане написання моделі. тоді `byModelTruncated` є істинним, і модель, пари якої потрапляють по обидва боки розрізу, показує часткові підсумки.
- Повідомляється про дві витрати. `costUsd` — виставлена вартість, як показує аналітика використання. Постачальники підписки з фіксованою ставкою, такі як план Claude Code, нараховують там 0 доларів. `listPriceUsd` — це те саме використання за роздрібною ціною, включаючи підписку. Запит, модель якого не має рядка ціни, підраховує свою збережену вартість: вартість, яку повідомив постачальник, або вартість, розраховану під час запису запиту. Лише запит із жодним не враховує 0, без маркера, тому підсумок може бути частковим.
- Контракт відповіді – `src/shared/schemas/selfUsage.ts` (`SelfUsageSeries` у `docs/openapi.yaml`).

### Сторінка самообслуговування

Якщо `QUOTA_SELF_PANEL` увімкнено, `/quota/{provider}` є публічною сторінкою. Власник ключа вводить там ключ API і бачить пули цього ключа для постачальника. Кожен пул показує одну картку на вікно пулу, з використанням пулу для всіх і власною часткою ключа. Кожен обліковий запис пулу має власні картки з використанням облікового запису та часткою ключа. Використання облікового запису відображається лише тоді, коли ключ може бачити дані облікового запису. На сторінці також перераховані обмеження для кожної моделі для кожного облікового запису та використання власного ключа. Якщо розклад блокує ключ прямо зараз, з’являється повідомлення. На картці перелічено всі ковпачки ключа для кожної моделі з його використанням і позначені досягнуті. `{provider}` — ідентифікатор провайдера або його псевдонім (`/quota/claude`, `/quota/cc`). Невідомий постачальник і кожен шлях `/quota/*`, поки прапорець вимкнено, відповідають 404. Пули на спеціальному вузлі, сумісному з OpenAI або Anthropic, не мають сторінки. API все ще відповідає за них.

Сторінка не має сесії. Ключ надсилається лише в заголовку `Authorization` для `GET /api/v1/me/quota/{provider}`, `PATCH /api/v1/me/quota/{provider}` і `GET /api/v1/me/usage`, а не в URL. Ключ, який приймає сервер, зберігається в `sessionStorage` вкладки. За допомогою «Запам’ятати на цьому пристрої» він зберігається в `localStorage`, а «Забути ключ» видаляє його з обох. Ключ, який сервер відхиляє, видаляється зі сховища.

Пул у режимі `consent` показує кредитну картку. Там власник ключа встановлює цілий відсоток від 0 до 100 неактивної частки ключа для позичання. Власник також вибирає, як довго діятиме згода: до вимкнення, 1 година, 8 годин, 24 години, 7 днів або 30 днів. Тривалість відраховується з моменту збереження. Поки діє термін, власник може його зберегти. Якщо цей крайній термін минає до збереження, картка нічого не надсилає та запитує інший вибір. З 0% крайній термін не надсилається. Картка показує збережений крайній термін із назвою часового поясу. Згода, термін дії якої минув, відображається як завершена.

Для ключа `hard` картка також перераховує, для вікна пулу, які інші ключі позичаються ключу прямо зараз. Кожен рядок — це одна фігура для всіх інших ключів разом. У наборі з двох ключів це фігура іншого ключа. Цифра, яку перегляд не повідомляє, читається як недоступна, а не як нуль. Для ключа `soft` або `burst` на картці зазначено, що цифра не застосовується.

Пул у режимі `saturation`, ключ якого зберігає відсоток вище 0, показує лише вилучення. Там сказано, що збережений відсоток тут не впливає. Його кнопка «Відкликати» надсилає 0 без крайнього терміну. Пул у режимі `saturation` із збереженим 0 показує відсутність кредитної картки. Після збереження картка, яка більше не потрібна повернутому перегляду, залишається з повідомленням, доки перегляд сторінки знову не зміниться.

Нічого не буде збережено, доки власник не натисне «Зберегти» або «Вилучити». Кожне натискання надсилає один запит `PATCH /api/v1/me/quota/{provider}`, а друге натискання нічого не надсилає, поки перше очікує на розгляд. Тіло несе непрозорий `ref` басейну від виду, відсоток і термін. Відповідь полягає в перебудованому перегляді квот, і сторінка відображає його без повторного читання. Коли два збереження збігаються, сторінка зчитує квоту один раз після останньої відповіді. Сторінка не зберігає згоду в сховищі браузера.

Відмова в зміні пояснюється на картці текстом, вибраним із статусу HTTP. Тіло помилки не читається. 401 повідомляє, що ключ не прийнято, і перезавантажує квоту. 403 говорить, що пул не приймає зміни кредитування, а 404 говорить, що пул зник. Обидва пропонують кнопку, яка перезавантажує квоту. 400 або інша відповідь 4xx просить власника перевірити відсоток і кінцевий термін. A 429 просить власника зачекати з секундами `Retry-After`, коли їх дає відповідь. Відповідь 5xx, 408 або збій мережі повідомляє, що зміни, можливо, не було збережено, і зберігає введені значення. Відповідь поза контрактом перезавантажує квоту. Невдале збереження не призводить до видалення ключа. Якщо після перезавантаження відхилено, сторінка видаляє ключ, як і під час будь-якого відхиленого читання.

Після прийняття ключа на сторінці також відображається картка «Налаштуйте свої інструменти» з трьома вкладками. "Код Claude " надає блок `env` для `~/.claude/settings.json`. "Shell" надає ті самі змінні, що й рядки `export`. "Claude Desktop" надає значення для вікна виводу третьої сторони. Ці моделі — це моделі розподілу квот, які ключ може викликати для цього постачальника. Якщо такого списку немає разом із ключем, блок замість цього вмикає виявлення моделі шлюзу. Адреса шлюзу — це публічне джерело API, яке повідомляє сервер (`OMNIROUTE_PUBLIC_API_BASE_URL`, потім `OMNIROUTE_PUBLIC_BASE_URL`). Якщо жодного з них не встановлено, на картці відображається заповнювач і повідомляє власнику запитати адміністратора. Ключ показано як заповнювач. «Включити мій ключ» поміщає весь ключ у текст на екрані та в те, що копіює кнопка копіювання. Це триває до тих пір, поки поле не буде очищено, ключ не буде забутий або замінений, або сторінка залишена. Картка не надсилає запитів і не пропонує завантаження файлів.

Показання API позначає `stale` як, можливо, застаріле. Зчитування, яке воно позначає як `unavailable` відображається разом із причиною, а не як нуль.

На відсоткових планах сторінка отримує власну частку ключа, коли про це повідомляє API. У ньому сказано, що число є оціночним і називаються дві його частини. Обмеження для кожної моделі показують лише обліковий запис.

Коли вікно містить `members`, його картка також показує смугу з одним сегментом на член у порядку слотів. Сегмент запитуваного ключа використовує акцентний колір. Інші сегменти чергуються між кольорами діаграми теми. Текстова легенда містить список кожного сегмента з його значенням, тому нічого не залежить від кольору. Сегменти позначаються `You` або `Member N`, де N — слот.

### Виділений порт для сторінки

`QUOTA_PANEL_PORT` відкриває другий слухач, який обслуговує лише сторінку самообслуговування. Він вимкнений, якщо змінна не встановлена. `QUOTA_PANEL_HOST` це адреса прив’язки, а за замовчуванням — `127.0.0.1`.

Слухач передає ці шляхи до головного порту та відповідає 404 для кожного іншого шляху:

| шлях                                                                     | Подає                                  |
| ------------------------------------------------------------------------ | -------------------------------------- |
| `/quota/{provider}`                                                      | Сторінка                               |
| `/api/v1/me/quota/{provider}`, `/v1/me/quota/{provider}`                 | Квота перегляду сторінки               |
| `/api/v1/me/usage`, `/v1/me/usage`                                       | Серія використання, яку читає сторінка |
| `/_next/static/`                                                         | Скрипти, стилі та шрифти збірки        |
| `/favicon.ico`, `/favicon.svg`, `/icon-512.png`, `/apple-touch-icon.png` | Ікони                                  |

`GET` і `HEAD` ретранслюються без тіла. Також передається один запит із тілом: `PATCH` шляху перегляду квоти, який сторінка надсилає, щоб зберегти вибір кредитування. Будь-який інший метод відповідає на 404, окрім запиту CONNECT, з’єднання якого закривається без відповіді. Будь-який інший запит, який оголошує тіло, відповідає 404, і його з’єднання закрито. Запити на оновлення відхиляються, а їх з’єднання закривається. Шлях із точковим сегментом або маркером фрагмента відхиляється, як у порту API. Так само як цільовий запит із символом поза друкованим ASCII. Синтаксичний аналізатор HTTP відповідає 400 на необроблений керуючий символ у цілі перед власною перевіркою цього порту. Заголовки запитів, які структура резервує для власного використання, не ретранслюються: імена, що починаються з `x-middleware-`, `x-invoke-`, `x-nextjs-`, `x-now-` або `x-next-`, а також імена `x-matched-path` і `next-resume`. Запит передається без них. Через цей порт неможливо отримати доступ до інформаційної панелі, сторінки входу, керування API та маршрутів висновків.

`PATCH` має містити `Content-Type: application/json` без параметра або лише з `charset=utf-8`. Він повинен містити один `Content-Length` від 1 до 4096, записаний простими цифрами, без `Transfer-Encoding`. `PATCH`, який порушує одне з цих правил, відповідає 404. На деякі неправильно сформовані довжини, такі як знакові або повторювані, аналізатор HTTP отримує відповідь 400 перед власною перевіркою цього порту. Порт зчитує оголошені байти перед тим, як зв’язатися з головним портом, і чекає їх не більше 5 секунд. Тіло, яке на той час не завершено, відповідає 404, і його зв’язок закривається. Ніщо не досягає головного порту в цьому випадку або коли клієнт виходить першим. Порт передає саме оголошені байти з однаковим `Content-Length`. Байти після них зчитуються як наступний запит на підключення. Зворотний проксі TLS попереду має пересилати `Content-Length` і не повинен повторно розбивати тіло запиту. Головний порт перевіряє ключ API у заголовку `Authorization`, як і для `GET`.

Корпус 404 – це `{"error":"not_found","message":"Not found."}`. Несправне реле відповідає 502 (`api_bridge_unavailable`) або 504 (`api_bridge_timeout`) без поля `detail`.

Слухач не читає `QUOTA_SELF_PANEL` і не відкриває сторінку. Поки прапор вимкнено, сторінка та її API відповідають 404 на головному порту, а слухач передає цю відповідь.

На сервері розробки (`next dev`) сторінка не стає інтерактивною через цей порт. Розетка для гарячої перезавантаження розробки є запитом на оновлення, і порт відхиляє його. Використовуйте основний порт під час розробки.

Порт обслуговує простий HTTP, а сторінка надсилає ключі API. Збережіть адресу прив’язки за замовчуванням і поставте перед нею зворотний проксі-сервер із TLS. Адреса прив’язки, відмінна від петлевої, реєструє це сповіщення:

```text
[Quota Panel] Bound to <host>. This port serves plain HTTP and the page sends API keys. Put a TLS reverse proxy in front of it.
```

Одноранговий вузол зворотного зв’язку, який не надсилає заголовок пересилання, вважається локальним на головному порту. Отже, проксі на тому самому хості повинен надіслати `X-Forwarded-For`. Проксі-сервер на приватній адресі є надійним для цього заголовка лише з `OMNIROUTE_TRUST_PROXY=private` (або `lan`). Про будь-який інший вузол повідомляється за адресою його з’єднання, а заголовки пересилання, які він надіслав, видаляються.

Слухач підтримує щонайбільше 256 підключень одночасно. Клієнт має 10 секунд, щоб надіслати заголовки запиту, і 30 секунд, щоб надіслати весь запит. Неактивне підтримуване підключення закривається приблизно через 5 секунд. З’єднання без активності протягом 60 секунд закривається. Ці значення є фіксованими. Також встановіть обмеження на з’єднання та швидкість на зворотному проксі-сервері спереду. Зворотний проксі-сервер має підтримувати неактивні висхідні підключення менше 5 секунд або не використовувати їх повторно. Ретрансляція до головного порту використовує вихідний тайм-аут порту API (`API_BRIDGE_*`).

Слухач також запускається, коли `API_PORT` не встановлено. `QUOTA_PANEL_PORT` має бути портом від 1 до 65535, написаним лише цифрами. Він має відрізнятися від порту приладової панелі та порту API. Поки живий сервер WebSocket увімкнено, він також має відрізнятися від `LIVE_WS_PORT` (за замовчуванням 20132). Будь-яке інше значення нічого не відкриває та записує попередження. Попередження про відхилене значення називає змінну й не повторює значення. Порт, який уже використовується, нічого не відкриває та записує це попередження:

```text
[Quota Panel] Port <port> is already in use. The quota panel port stays off.
```

Якщо встановити `OMNIROUTE_BASE_PATH`, слухач очікує кожен шлях вище під цим префіксом. Використовуйте той самий `OMNIROUTE_BASE_PATH` під час збирання та під час виконання. Напишіть його з похилою рискою на початку та без похилої риски в кінці, наприклад `/omniroute`. Інша форма, включаючи `/` і `/omniroute/`, залишає порт вимкненим із попередженням, хоча збірка приймає ці форми. Так само і базовий шлях, перший сегмент якого називає маршрут програми: `api`, `v1`, `v1beta`, `_next`, `quota`, `dashboard`, `docs`, `login`, `codex`, `responses`, `anthropic`, `openai`, `v0` або `connect`, у будь-якому випадку.

Обмеження:

- `/quota/{provider}/` з косою рискою в кінці відповідає 404 на цьому порту.
- Сервіс-воркер і маніфест веб-програми не обслуговуються на цьому порту.
- Спеціальна піктограма сайту на інформаційній панелі не відображається на цьому порту.
- Піктограми не відображаються, якщо програма працює за базовим шляхом.
- Порт розмовляє простим HTTP/1.1.
- Невдале прив’язування не повторюється, доки процес не перезапуститься.
- Слухач не має обмежень на з’єднання чи швидкість на адресу клієнта.
- У цьому розділі не розглядаються налаштування контейнерів.

## Усунення несправностей

### Redis налаштовано, але підключення не встановлюється

Перевірте, чи встановлено `ioredis` (`npm ls ioredis`) і чи доступна адреса
`QUOTA_STORE_REDIS_URL`. У разі помилки підключення фабрика повертається до SQLite
(це реєструється на рівні `warn`).

### `peek` повертає застарілі дані / працює у відкритому режимі в разі збою

Якщо `peek` спричиняє виняток, `enforceQuotaShare` трактує результат як «дозволити»
(відкритий режим у разі збою). Перевірте журнали `pino` на наявність записів
`quota:enforce` і `quota:factory`, щоб визначити першопричину.

### Розбіжність лічильника споживання

Якщо фактичне використання в постачальника відрізняється від показників лічильників,
це очікувано — ковзне вікно з 2 сегментів має похибку ~1% на межах вікна, а `consume`
виконується асинхронно після надсилання відповіді без очікування результату. Сигнал
насичення (`saturationSignals.ts`) зчитує фактичну утилізацію ресурсів постачальника
з TTL 30 с і відповідно коригує `globalUsedPercent`.

### Пул показує «немає даних» для швидкості споживання

`computeBurnRate` потребує щонайменше 2 історичних зразків. Нові пули без попередніх
викликів `consume` показуватимуть `tokensPerSecond: 0` і `timeToExhaustionMs: null`.

## Міграція з localStorage

Під час першого завантаження `/dashboard/costs/quota-share` хук `useLocalStoragePoolMigration`
перевіряє:

1. `localStorage.getItem("omniroute:quota-share:pools")` не є порожнім.
2. `GET /api/quota/pools` повертає `[]` (БД порожня).

Якщо обидві умови виконуються, він пакетно надсилає кожен застарілий пул до `POST /api/quota/pools`,
а потім видаляє ключ localStorage. Міграція є ідемпотентною: умова 2 запобігає
повторній міграції.

## Внутрішня класифікація стратегії

`quota-share` — це стратегія маршрутизації **лише для внутрішнього використання** (`INTERNAL_ROUTING_STRATEGY_VALUES` у
`src/shared/constants/routingStrategies.ts`). Вона використовується виключно створеними системою
комбінаціями пулів `qtSd/` і навмисно виключена з `ROUTING_STRATEGY_VALUES`, тому ніколи
не з'являється як доступний користувачеві варіант у UI або API.

## Резюме схеми DB

Три таблиці, додані міграціями `078`, `079` і `085`:

- `quota_pools` + `quota_allocations` — визначення пулу та виділення для кожного ключа.
- `quota_consumption` — рухомі 2-ковшові лічильники на `(apiKeyId, dimensionKey)`.
- `provider_plans` — ручні перевизначення плану постачальника (розміри JSON на connectionId).

Усі таблиці додано за допомогою ідемпотентних міграцій `CREATE TABLE IF NOT EXISTS`.

Позика за згодою додає три стовпці: `quota_allocations.lending_percent` (ціле число, за замовчуванням 0), `quota_allocations.lending_until` (епоха мілісекунди або `NULL` без кінцевого терміну) і `quota_pools.borrow_mode` (за замовчуванням `saturation`). Його міграція лише додає ці стовпці та не записує жодного існуючого рядка.

Книга відсотка атрибуції додає `quota_percent_ledger` (один рядок на пул, обліковий запис і вікно плану) і `quota_percent_ledger_tokens` (один лічильник токенів на пул, обліковий запис і ключ API ). `src/lib/db/quotaPercentLedger.ts` читає та записує їх.
