## ସଂକ୍ଷିପ୍ତ ସାରାଂଶ

```bash
# 1. ସଂସ୍କରଣ ବଢ଼ାନ୍ତୁ + CHANGELOG ସୃଷ୍ଟି କରନ୍ତୁ (skill)
/version-bump-cc patch    # କିମ୍ବା minor/major

# 2. ସ୍ଥାନୀୟ ଭାବେ quality gate ଚଲାନ୍ତୁ
npm run check              # lint + tests
npm run test:coverage      # ସମ୍ପୂର୍ଣ୍ଣ coverage gate (60/60/60/60)

# 3. Build କରନ୍ତୁ ଏବଂ smoke test ଚଲାନ୍ତୁ
npm run build
npm run test:e2e           # ବୈକଳ୍ପିକ, କିନ୍ତୁ ସୁପାରିଶକୃତ

# 4. release ସୃଷ୍ଟି କରନ୍ତୁ (skill)
/generate-release-cc

# 5. Deploy କରନ୍ତୁ (skill)
/deploy-vps-both-cc        # କିମ୍ବା akamai-cc / local-cc

# 6. release evidences ସଂଗ୍ରହ କରନ୍ତୁ (skill)
/capture-release-evidences-cc
```

## npm ବିଶ୍ୱସ୍ତ ପ୍ରକାଶନ (v3.8.51 ପରଠାରୁ ଡିଫଲ୍ଟ) — ଅନୁରୋଧ ଅନୁଯାୟୀ ଷ୍ଟେଜ୍ ହୋଇଛି, ସିଧାସଳଖ ଫଲବ୍ୟାକ୍ ଭାବରେ।

`npm-publish.yml` ମାଧ୍ୟମରେ ପ୍ରକାଶ କରେ।** npm ବିଶ୍ୱସ୍ତ ପ୍ରକାଶନ (OIDC)** ଡିଫଲ୍ଟ ଭାବରେ: `stage-npm` କାର୍ଯ୍ୟ (ଗିଥବ୍-ହୋଷ୍ଟ) GitHub ର id- ଟୋକେନ୍ କୁ ସ୍ୱଳ୍ପ ସମୟର npm ପ୍ରମାଣପତ୍ର ପାଇଁ ବିନିମୟ କରେ — ରେପୋଜିଟୋରୀ ରହସ୍ୟରେ ଦୀର୍ଘସ୍ଥାୟୀ npm ଟୋକେନ୍ ନାହିଁ, 2FA ପ୍ରମ୍ପ୍ଟ, ପ୍ରୋଭାନ୍ସ ସଂଲଗ୍ନ ହୋଇନାହିଁ। ତାହା ହେଉଛି ବାଇପାସ୍ npm ପ୍ରତିବନ୍ଧକ ବର୍ତ୍ତମାନ 2FA ଛାଡିଥିବା ଟୋକେନ୍ ଗୁଡିକ ଅବସରପ୍ରାପ୍ତ; WS1.3 ଗ୍ୟାରେଣ୍ଟି ରଖିବାବେଳେ ଏହା ପ୍ରକଳ୍ପର ସମ୍ପୂର୍ଣ୍ଣ ସ୍ୱୟଂଚାଳିତ ପ୍ରବାହକୁ ପୁନ ores ସ୍ଥାପନ କରିଥାଏ —

**ଗୋଟିଏ ଥର ସେଟଅପ୍ (ମାଲିକ):** npmjs.com → ପ୍ୟାକେଜ୍ `omniroute` → ସେଟିଂସମୂହ → ବିଶ୍ୱସ୍ତ ପ୍ରକାଶକ_ → GitHub: ମାଲିକ `diegosouzapw`, ରେପୋ `OmniRoute`, କାର୍ଯ୍ୟ ପ୍ରବାହ `npm-publish.yml` (ପରିବେଶ: କିଛି ନୁହେଁ)। ଯେପର୍ଯ୍ୟନ୍ତ ତାହା ବିଦ୍ୟମାନ ନାହିଁ, ସ୍ୱୟଂଚାଳିତ ପଦକ୍ଷେପ `ENEEDAUTH` ସହିତ ବିଫଳ ହୁଏ: `publish_mode=staged` (ତଳେ) କିମ୍ବା `direct` ସହିତ ପୁନ - ପଠାନ୍ତୁ।

### ପର୍ଯ୍ୟାୟ ପ୍ରକାଶନ ( — `publish_mode=staged` ଅନୁରୋଧରେ)

Npm- ପ୍ରକାଶନ କାର୍ଯ୍ୟ ପ୍ରବାହ ଆଉ ସିଧାସଳଖ ପ୍ରକାଶ କରେ ନାହିଁ: ଏହା ପ୍ୟାକ୍ ହୋଇଥିବା ଟାରବଲ୍ (`check:pack-boot`) କୁ ବୁଟ୍ କରେ ଏବଂ ତା’ପରେ `npm stage publish` — ଚଲାଇଥାଏ ସଠିକ୍ ବାଇଟ୍ ରେଜିଷ୍ଟ୍ରିରେ ପାର୍କ ହୋଇଛି,** ସଂସ୍ଥାପିତ ନୁହେଁ।** ଯେପର୍ଯ୍ୟନ୍ତ ମାଲିକ ଅନୁମୋଦନ ନକରନ୍ତି। ମାନବ 2FA ଗେଟ୍ ପ୍ରମାଣ ପୂର୍ବରୁ AFTER କୁ ଚାଲିଗଲା।

**କାର୍ଯ୍ୟ ପ୍ରବାହ ସବୁଜ ହେବା ପରେ ମାଲିକ ପ୍ରବାହ:**

1. `npm stage list omniroute` — ଷ୍ଟେଜ୍ id ଖୋଜ (ୱାର୍କଫ୍ଲୋ ସାରାଂଶରେ ମଧ୍ୟ ମୁଦ୍ରିତ)।
2. ଷ୍ଟେଜ୍ ହୋଇଥିବା ବାଇଟ୍ ଯାଞ୍ଚ କରନ୍ତୁ (ପରାମର୍ଶିତ): `npm stage download <id>`, ତାପରେ ଡାଉନଲୋଡ୍ ହୋଇଥିବା ଟାରବଲ୍ କୁ ଏକ ଟେମ୍ପ୍ ଉପସର୍ଗରେ ସଂସ୍ଥାପନ କରନ୍ତୁ ଏବଂ ଏହାକୁ ବୁଟ କରନ୍ତୁ (`npm run check:pack-boot` ସମାନ ପ୍ୟାକ୍→ ସ୍ୱୟଂଚାଳିତ → ବୁଟ ବିଚାରକୁ CI ରେ ସ୍ଥାପନ କରିଥାଏ)।
3. `npm stage approve <id>` — 2FA ପ୍ରମ୍ପ୍ଟ IS ପ୍ରକାଶନ। `npm stage reject <id>` ପରିତ୍ୟାଗ କରେ।
4. ପୋଷ୍ଟ-ପ୍ରକାଶନ ନେଟ: ପୋଷ୍ଟ-ପ୍ରକାଶନ ଯାଞ୍ଚକାରୀ (v3.8.49 ଯୋଜନାର WS1.4) ସର୍ବସାଧାରଣ ସଂସ୍କରଣରୁ ପ୍ରକାଶିତ ସଂସ୍କରଣକୁ ଏକ ପରିଷ୍କାର ପାତ୍ରରେ ସଂସ୍ଥାପନ କରେ ଏବଂ ଏହାକୁ ବୁଟ୍ କରେ।

**ଜରୁରୀକାଳୀନ ଅବନତି:** `publish_mode=direct` ସହିତ `workflow_dispatch` ଉତ୍ତରାଧିକାରୀ ତୁରନ୍ତ `npm publish` ପୁନ ores ସ୍ଥାପନ କରେ (ଯଦି ନିଜକୁ ଭୁଲ୍ ବ୍ୟବହାର କରେ ତେବେ ବ୍ୟବହାର କର; କାହିଁକି ରେକର୍ଡ କର)।

**One-time hardening (owner, npmjs.com):** configure the Trusted Publisher for `omniroute` in stage-only mode so a leaked long-lived token cannot `npm publish` directly from anywhere — CI can only stage; only the owner's 2FA releases.

**ଭଙ୍ଗା-ଆର୍ଟିଫାକ୍ଟ ପ୍ଲେବୁକ୍ (ଅପରିବର୍ତ୍ତିତ):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ଡିଫଲ୍ଟ ରିଫ୍ଲେକ୍ସ ଭାବରେ (ମିନିଟ୍, ଓଲଟା); `npm unpublish` କେବଳ 72h/no-dependents ୱିଣ୍ଡୋ ଭିତରେ ଏବଂ ପ୍ରଥମ ପଦକ୍ଷେପ ଭାବରେ କେବେବି ନୁହେଁ। Docker: କ version ଣସି ସଂସ୍କରଣ ଟ୍ୟାଗ୍ ପୁନ rew ଲିଖନ କରନ୍ତୁ — ରୋଲବ୍ୟାକ୍ `latest` କୁ ଶେଷ ଭଲ ହଜମକୁ ପୁନ rep ନିଯୁକ୍ତ କରୁଛି।

**Docker ହବ୍ `latest` (ପ୍ରତ୍ୟେକ ସ୍ଥିର SemVer ପ୍ରକାଶନରେ ଆବଶ୍ୟକ):** `docker-publish` ୱାର୍କଫ୍ଲୋ ନିଶ୍ଚିତ ଭାବରେ ଟ୍ୟାଗ୍ କରିବ।** ଉଭୟ** `X.Y.Z` ଏବଂ, ଯେତେବେଳେ `should-promote-latest.sh` ରାଜି ହୁଏ ଏହା ହେଉଛି ସର୍ବୋଚ୍ଚ ସ୍ଥିର SemVer, `:latest` ସହିତ।** ସମାନ ହଜମ** । ଚାକିରି ପରେ: ହବ୍ `latest` digest ନୂତନ SemVer digest ସହିତ ସମାନ ଏବଂ `last_updated` ଘୁଞ୍ଚିଗଲା। `:latest` ଏକ ପୁରୁଣା ବିଲ୍ଡରେ ଛାଡନ୍ତୁ ନାହିଁ ଯେତେବେଳେ ରିଲିଜ୍ ନୋଟଗୁଡିକ ଫିକ୍ସ ବିଷୟରେ କଥାବାର୍ତ୍ତା କରେ ଯାହା କେବଳ git ରେ ବିଦ୍ୟମାନ। `:latest` ବ୍ୟବହାର କରୁଥିବା ଦ୍ରୁତ ଗତିରେ ରଚନା କରନ୍ତୁ; GitOps `X.Y.Z` ପିନ୍ କରିବା ଉଚିତ୍। [Docker ରିଲିଜ୍ ଚ୍ୟାନେଲ](../guides/DOCKER_GUIDE.md#release-channels) ଏବଂ #10317 ଦେଖନ୍ତୁ।

**Docker ହବ୍ ସଂଗଠନ ସଂଗ୍ରହାଳୟ (`cheaperinference/omniroute`):** Docker ହବ୍ ନାମ ସ୍ଥାନଗୁଡ଼ିକ ମଧ୍ୟରେ ଏକ ସଂଗ୍ରହାଳୟ ଘୁଞ୍ଚାଇ ପାରିବ ନାହିଁ, ତେଣୁ `diegosouzapw/omniroute` ଏହାର ଟାଣ ଇତିହାସ ଏବଂ ପ୍ରତ୍ୟେକ ପ୍ରକାଶନକୁ ରଖେ, ଏବଂ `docker-publish` ର `mirror-org-dockerhub` କାର୍ଯ୍ୟ ପ୍ରତ୍ୟେକ ପ୍ରକାଶିତ ସଂସ୍କରଣକୁ (ଏବଂ ପ୍ରୋତ୍ସାହିତ ହେଲେ `:latest` ) `ghcr.io/cheaper-inference/omniroute` ରୁ ସଂଗଠନ ସଂଗ୍ରହାଳୟକୁ କପି କରିଥାଏ। ଏହା `DOCKERHUB_ORG_USERNAME` / `DOCKERHUB_ORG_TOKEN` ରହସ୍ୟ ଆବଶ୍ୟକ କରେ; ସେମାନଙ୍କ ବିନା କାର୍ଯ୍ୟ ଏକ "Docker Hub org ମିରର୍ ସ୍କିପ୍" ଚେତାବନୀ ସହିତ ସବୁଜ ରହେ ଏବଂ ଅନ୍ୟ ରେଜିଷ୍ଟ୍ରିଗୁଡିକ ସାଧାରଣ ଭାବରେ ପ୍ରକାଶ କରେ। ପରେ ସେଠାରେ ଏକ ପ୍ରକାଶିତ ସଂସ୍କରଣ ପ୍ରକାଶ କରିବାକୁ, ଚଲାନ୍ତୁ।** କାର୍ଯ୍ୟଗୁଡ଼ିକ → ଦର୍ପଣ Docker ପ୍ରତିଛବି Docker ହବ୍ org → କାର୍ଯ୍ୟଧାରା ଚଲାନ୍ତୁ।** `version=X.Y.Z` ସହିତ (ଏବଂ ସର୍ବୋଚ୍ଚ ସ୍ଥିର ସଂସ୍କରଣ ପାଇଁ `promote_latest` ): ଏହା ବିଦ୍ୟମାନ ପ୍ରତିଛବିଗୁଡ଼ିକୁ ନକଲ କରେ, ପୁନ build ନିର୍ମାଣ ନାହିଁ। ସେହି ସଂଗ୍ରହାଳୟର Docker ହବ୍ ପୂର୍ବାବଲୋକନ ହାତରେ ସେଟ୍ ହୋଇଛି: ଏହାକୁ ସଂପାଦନ କରୁଥିବା API ସଂଗଠନ ଆକ୍ସେସ୍ ଟୋକେନ୍ଗୁଡ଼ିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

ସମାନ କାର୍ଯ୍ୟ ପ୍ରବାହ ମଧ୍ୟ 2027-06-30 ପର୍ଯ୍ୟନ୍ତ ଉତ୍ତରାଧିକାରୀ GHCR ପ୍ୟାକେଜ୍ `ghcr.io/diegosouzapw/omniroute` କୁ ପ୍ରତ୍ୟେକ ପ୍ରକାଶନକୁ କପି କରିଥାଏ, ତେଣୁ ଏହାକୁ ଅଦ୍ୟତନ କରିବା ପାଇଁ ଏପର୍ଯ୍ୟନ୍ତ ପିନ୍ ହୋଇଥିବା ସଂସ୍ଥାଗୁଡ଼ିକ; ଏହାର ସୂଚକାଙ୍କ ଏକ " `ghcr.io/cheaper-inference/omniroute` କୁ ସ୍ଥାନାନ୍ତରିତ" ବର୍ଣ୍ଣନା ବହନ କରେ। ଏହା `GHCR_LEGACY_TOKEN` ଗୁପ୍ତ ଆବଶ୍ୟକ କରେ ( `write:packages` ସହିତ `diegosouzapw` ର ଏକ କ୍ଲାସିକ୍ ବ୍ୟକ୍ତିଗତ ପ୍ରବେଶ ଟୋକନ୍); ଏହା ବିନା ଚାକିରି ଏକ "Legacy GHCR ମିରର୍ ସ୍କିପ୍" ଚେତାବନୀ ସହିତ ଛାଡିଦିଏ।

quality-gate, quality-extended) କୁ ଛାଡ଼ି ଦିଏ ଏବଂ ଦ୍ରୁତ, ଉଚ୍ଚ-ସିଗ୍ନାଲ୍ ଗେଟ୍ଗୁଡ଼ିକୁ ରଖେ: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
ଏବଂ tarball boot-smoke (`check:pack-boot`)। ଲକ୍ଷ୍ୟ: ପ୍ରାୟ 33 ମିନିଟ୍ ପରିବର୍ତ୍ତେ ≤15 ମିନିଟ୍ରେ ସବୁଜ।

**ପ୍ରବେଶ ନୀତି — ଚାରୋଟି ଯାକ ଆବଶ୍ୟକ (Chromium/VS Code/Node ଜରୁରୀ ଲେନ୍ଗୁଡ଼ିକ ଆଧାରିତ):**

1. **ଗୁରୁତ୍ୱ**: ପ୍ରଡକ୍ସନ୍ ଭାଙ୍ଗିଯାଇଛି — ପ୍ରକାଶିତ artifact boot ସମୟରେ crash କରୁଛି / ଏକ
   security fix / release ର ପ୍ରତ୍ୟେକ user ପ୍ରଭାବିତ। "ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ" ମାନେ "ଭାଙ୍ଗିଯାଇଛି" ନୁହେଁ।
2. **କର୍ତ୍ତୃତ୍ୱ**: କେବଳ repository owner `hotfix` ଲେବଲ୍ ପ୍ରୟୋଗ କରନ୍ତି। ଲେବଲ୍ଟି ହିଁ
   ଅନୁମୋଦନ — campaign PR ରେ କେବେବି ନିଜେ ଲେବଲ୍ ଲଗାନ୍ତୁ ନାହିଁ।
3. **ପ୍ରମାଣ**: PR body ରେ ପୂର୍ବରୁ ସମ୍ପୂର୍ଣ୍ଣ ସବୁଜ ଥିବା heavy run ର ଲିଙ୍କ୍ (ଯେଉଁ suite କୁ
   ଛାଡ଼ାଯାଇଥିବା jobs ପୁନଃ ଯାଞ୍ଚ କରିଥାନ୍ତେ) ସହିତ fix ର ନିଜସ୍ୱ failing-then-passing test ର ଲିଙ୍କ୍ ଥାଏ।
4. **ପରିସର**: କେବଳ cherry-pick — ନ୍ୟୁନତମ fix, କୌଣସି refactor ନୁହେଁ, କୌଣସି ride-along ନୁହେଁ।

ଛାଡ଼ାଯାଇଥିବା coverage/ratchet surface କୁ release branch ର ପରବର୍ତ୍ତୀ full run ଦ୍ୱାରା
ପୁନଃ ଯାଞ୍ଚ କରାଯାଏ (continuous release-green) — ଏହି lane WAITING କୁ ଛାଡ଼େ, validation କୁ ନୁହେଁ।
କେବଳ tests-only diff (ସମସ୍ତ files `tests/` ଅଧୀନରେ, `tests/e2e/` ଅଧୀନରେ କୌଣସି file ନାହିଁ)

  - release branches push କରିବା ପୂର୍ବରୁ `npm run test:unit` ମାନୁଆଲ୍ ଭାବେ ଚଲାନ୍ତୁ।

### Build Layout

Repository ତିନୋଟି ପୃଥକ output directory ବ୍ୟବହାର କରେ — ସେଗୁଡ଼ିକୁ କେବେବି ମିଶାନ୍ତୁ ନାହିଁ:

| Directory | Purpose                                                      | Tracked?        |
| --------- | ------------------------------------------------------------ | --------------- |
| `src/`    | Application source (TypeScript / TSX)                        | ହଁ              |
| `.build/` | Build intermediates — `next build` output (`distDir`)        | ନା (gitignored) |
| `dist/`   | Shippable npm bundle — `assembleStandalone` ଦ୍ୱାରା assembled | ନା (gitignored) |

> **Operator note:** remote VPS image directory ଏବେ ମଧ୍ୟ `/usr/lib/node_modules/omniroute/app/` ଅଟେ।
> କେବଳ **in-repo** build output ପରିବର୍ତ୍ତିତ ହୋଇଛି (`app/` → `dist/`)। Deploy skills
> `dist/` ର contents କୁ remote `app/` dir ଭିତରେ rsync କରେ — କୌଣସି VPS path ପରିବର୍ତ୍ତନ ଆବଶ୍ୟକ ନାହିଁ।

**Single-build flow:**

```
npm run build:release
  └─ rm -rf .build dist          (clean)
  └─ next build → .build/next/   (intermediates)
  └─ assembleStandalone          (copies standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (HEAD sentinel)
```

Deploy ପାଇଁ `npm run build` ପରେ ପୃଥକ ଭାବରେ `npm run build:cli` ଚଲାନ୍ତୁ ନାହିଁ — ଏକ command ରେ clean rebuild + sentinel କରୁଥିବା `npm run build:release` ବ୍ୟବହାର କରନ୍ତୁ।

`scripts/release/artifact-identity.mjs`) ରେକର୍ଡ କରେ ଏବଂ ଏକ ପୃଥକ job ରେ tarball କୁ attest କରେ। Preview କୁ promote କରିବାର ଅର୍ଥ ହେଉଛି ସେହି tarball କୁ install କରିବା: source ରୁ କେବେ ମଧ୍ୟ ପୁନଃbuild କରନ୍ତୁ ନାହିଁ।

### କଟ୍ (3.9.0, GO ପରେ)

1. [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md) ରେ GO ରେକର୍ଡ କରାଯାଇଛି।
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` `RESULT: READY` ପ୍ରିଣ୍ଟ କରେ।
3. Dry-run ଯେଉଁ commands ପ୍ରିଣ୍ଟ କରେ ସେଗୁଡ଼ିକ ସହିତ `origin` ଉପରେ branch ଗୁଡ଼ିକୁ ହାତରେ create କରନ୍ତୁ — script `origin` କୁ push କରିବାକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ସମୀକ୍ଷା କରାଯାଇଥିବା develop commit କୁ ପୁନଃବ୍ୟବହାର କରିବାକୁ, ପ୍ରଥମେ ଆପଣଙ୍କ fork ବିରୋଧରେ 3.9.0 tip ଉପରେ `--execute` rehearsal ଚଲାନ୍ତୁ; ଏହା ଉଭୟ SHA ପ୍ରିଣ୍ଟ କରେ, ଏବଂ
   ସେହି commit ଗୁଡ଼ିକୁ push କରାଯାଇପାରେ:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. ପ୍ରଥମ PR ଆସିବା ପୂର୍ବରୁ `stable/v3` ଏବଂ `develop`କୁ ସୁରକ୍ଷିତ କରନ୍ତୁ (ନିୟମସେଟ୍ + ମର୍ଜ୍ କ୍ୟୁ)।
5. ନିଷ୍କ୍ରିୟ ୱର୍କଫ୍ଲୋଗୁଡ଼ିକ ବ୍ରାଞ୍ଚ୍ ଥିବା ଆଧାରରେ ସକ୍ରିୟ ହୁଅନ୍ତି: `forward-port.yml` (`stable/v3`କୁ push), `validate-stable-pr.yml` (`stable/v3`କୁ PRଗୁଡ଼ିକ) ଏବଂ `nightly-v4-build.yml`
   (`develop`ର buildଗୁଡ଼ିକ)। go-live ପୂର୍ବରୁ, ରିପୋଜିଟରି ସିକ୍ରେଟ୍ `secrets.FORWARD_PORT_TOKEN` ସେଟ୍ କରନ୍ତୁ (ଯାହାଦ୍ୱାରା CI
   forward-port PRଗୁଡ଼ିକରେ ଚାଲିବ); ମାଲିକ ରିପୋଜିଟରି ଭେରିଏବଲ୍ `vars.NIGHTLY_PUBLISH`କୁ `true` ସେଟ୍ ନ କରିବା ପର୍ଯ୍ୟନ୍ତ ଏବଂ npm Trusted Publishing `nightly-v4-build.yml`କୁ ଗ୍ରହଣ ନ କରିବା ପର୍ଯ୍ୟନ୍ତ ରାତ୍ରିକାଳୀନ ପ୍ରକାଶନ ବନ୍ଦ ରହିବ। ଚ୍ୟାନେଲ୍ ରିଜଲ୍ୟୁସନ୍ `scripts/release/dist-tag.mjs`ରେ ଅଛି, ଯାହା `npm-publish.yml` ବ୍ୟବହାର କରୁଥିବା ସେହି ରିଜଲ୍ଭର୍।
6. ଚ୍ୟାନେଲ୍ଗୁଡ଼ିକ ଯାଞ୍ଚ କରନ୍ତୁ: `npm view omniroute dist-tags --json` ଦେଖାଏ ଯେ `latest` = 3.9.0 ଏବଂ v4 ପ୍ରକାଶିତ ହେବା ପର୍ଯ୍ୟନ୍ତ `next` / `nightly` ନାହିଁ।
7. ଆବଶ୍ୟକ ହେଲେ ରୋଲବ୍ୟାକ୍ କରନ୍ତୁ: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   ଏବଂ `npm dist-tag add omniroute@3.8.59 latest`।

## ରୋଲବ୍ୟାକ୍

ରିଲିଜ୍ରେ ଗୁରୁତର ସମସ୍ୟା ଥିଲେ:

1. `gh release edit vX.Y.Z --prerelease` (ଏହାକୁ ସର୍ବଶେଷ ରିଲିଜ୍ ଭାବେ ଚିହ୍ନିତ ନକରିବା ପାଇଁ)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (କେବଳ ଯଦି ଏପର୍ଯ୍ୟନ୍ତ ବ୍ୟବହାରକାରୀମାନେ ଏହାକୁ ଗ୍ରହଣ କରିନାହାନ୍ତି)
3. କିମ୍ବା: `release/vX.Y.0` ଉପରେ ହଟଫିକ୍ସ → ପ୍ୟାଚ୍ ରିଲିଜ୍ `vX.Y.(Z+1)`
4. ତୁରନ୍ତ GitHub Discussions ଏବଂ Discord ରେ ସୂଚନା ଦିଅନ୍ତୁ

## କଠୋର ନିୟମ

- କେବେବି `main` ରେ ସିଧାସଳଖ କମିଟ୍ କରନ୍ତୁ ନାହିଁ
- `main` କିମ୍ବା `release/*` ବ୍ରାଞ୍ଚଗୁଡ଼ିକରେ କେବେବି `git push --force` ବ୍ୟବହାର କରନ୍ତୁ ନାହିଁ
- କେବେବି Husky ହୁକ୍ଗୁଡ଼ିକୁ (`--no-verify`) ଏଡ଼ାଇବେ ନାହିଁ
- କେବେବି ସିକ୍ରେଟ୍, ପ୍ରମାଣପତ୍ର କିମ୍ବା `.env` ଫାଇଲ୍ କମିଟ୍ କରନ୍ତୁ ନାହିଁ
- କଭରେଜ୍ ≥60/60/60/60 (ଷ୍ଟେଟମେଣ୍ଟ/ଲାଇନ୍/ଫଙ୍କସନ୍/ବ୍ରାଞ୍ଚ) ରହିବା ଆବଶ୍ୟକ
- `src/`, `open-sse/`, `electron/` କିମ୍ବା `bin/` ରେ ପ୍ରଡକ୍ସନ୍ କୋଡ୍ ବଦଳାଇବା ସମୟରେ ସର୍ବଦା ଟେଷ୍ଟ୍ ସାମିଲ କରନ୍ତୁ କିମ୍ବା ଅଦ୍ୟତନ କରନ୍ତୁ
